# Language Review

Language Review — локальная CLI-утилита для инвентаризации файлов, структурного извлечения человекочитаемых фрагментов из исходников и документации и языковой проверки русского технического текста.

## Возможности этого этапа

Утилита перечисляет поддерживаемые файлы, определяет тип файла, кодировку с учётом BOM, переводы строк, размер и базовую читаемость. Команда `extract` сохраняет происхождение выбранных фрагментов, точные диапазоны исходных файлов, SHA-256 и защищённые машинные вставки. Команда `check` передаёт эти фрагменты LanguageTool, Vale и LLM (Gemma 4 E4B через `llama-server` или Ollama), проверяет и согласует замечания и возвращает отчёт с точными координатами исходника. Команды `config show` и `doctor` показывают эффективные настройки и проверяют внешние программы, локальные HTTP-сервисы и языковые движки.

Извлечение поддерживает комментарии и контекстные строки Rust, C#, C и C++, PowerShell (`.ps1`, `.psm1`), Markdown, обычный текст, reStructuredText и AsciiDoc. Для `.json`, `.yaml`, `.yml`, `.toml` и `.xml` нужно явно включить расширение и настроить селекторы. `.psd1` не разбирается как исполняемый код. Неоднозначный синтаксис и повреждённые файлы помечаются, а не объявляются успешными пустыми результатами.

`extract` и `check` только читают исходники: предложенные исправления не применяются и требуют ручной проверки. SARIF, анализ Git diff и применение исправлений не реализованы.

Дополнительно доступна [предметная память](docs/memory.md): PostgreSQL/pgvector через
Docker Compose, автоматический журнал `check`, явные решения `decide-review`, фоновая
LLM-консолидация и гибридный recall перед следующим анализом. Память включается явно,
не требует действий агента для сохранения каждой находки и не подтверждает гипотезы
по уверенности модели. Без неё базовая установка работает без Docker.

Для агента-разработчика доступно [представление результатов ревью](docs/agent-review.md):
`check --view review` показывает приоритеты проверки, отдельные свидетельства и риски;
`--format json` выдаёт контракт `language-review.review` 1.0. `show-review` читает сохранённый
отчёт без повторного анализа, `verify-review` сверяет SHA-256, цитаты и координаты с исходниками.

Для измерений и регрессий доступен [независимый оценщик](docs/evaluation.md)
`language-review-eval`: валидируемый корпус, offline scoring сохранённых check/review,
раздельные detection/correction и coverage, сравнение baseline/candidate, ручные решения
и явный live capture. Включённый синтетический набор проверяет контракты оценщика;
независимая оценка на реальном русском техническом корпусе пока не выполнена.
Слепой пакет разметки 2.0 поддерживает постоянные `label_id` и альтернативы одной
ошибки; старые пакеты читаются без переименования меток. Подтверждённое согласие
разметчиков отделено от чернового, а полная оценка требует полного охвата случая.
Версии метрик и правила пересчёта сохранённых отчётов описаны в том же руководстве.

## Установка и запуск в PowerShell

Нужны Python 3.15 и uv 0.13.1 или новее. В репозитории выбрана последняя стабильная версия Python, доступная на момент подготовки этапа; пакет требует Python 3.15 или новее. Зависимости и версии инструментов разработки зафиксированы в `uv.lock`.

На Windows с Python 3.15 текущая версия `tree-sitter` из `uv.lock` устанавливается из исходников: для `uv sync` требуется компилятор MSVC из Visual Studio Build Tools с компонентами C++.

~~~powershell
uv sync --locked
uv run --locked language-review --help
uv run --locked language-review --version
uv run --locked python -m language_review --version
~~~

После `uv sync` команду можно запускать из активированного окружения:

~~~powershell
.venv\Scripts\Activate.ps1
language-review --help
~~~

## Команды

### Инвентаризация

~~~powershell
language-review scan .\src
language-review scan .\Cargo.toml .\README.md
language-review scan .\repo --format json
language-review scan .\repo --format json --output .\report.json
language-review extract .\src --format json
language-review extract .\settings.json --extension .json --format json
~~~

Формат по умолчанию — человекочитаемый. JSON содержит `schema_version`, сведения о программе и корнях, массив `files`, итоговые счётчики и статус обхода. Записи файла имеют состояния `selected`, `skipped` или `error`; языковых находок в схеме нет. При `--format json` stdout содержит только JSON, диагностика выводится в stderr.

По умолчанию учитываются `.rs`, `.cs`, `.cpp`, `.cc`, `.cxx`, `.c`, `.h`, `.hpp`, `.hh`, `.hxx`, `.ps1`, `.psm1`, `.md`, `.markdown`, `.txt`, `.rst` и `.adoc`. Новые расширения можно добавить через `--extension .toml`; `--only-extension` задаёт список вместо настроенного. Файлы с неподдерживаемым расширением, бинарным содержимым, неподходящей кодировкой или превышением лимита попадут в список пропусков с причиной.

### Извлечение текста

~~~powershell
language-review extract .\repo
language-review extract .\repo --format json
language-review extract .\repo --format json --output .\extract-report.json
language-review extract .\settings.json --extension .json --format json
~~~

`extract` использует тот же обход, фильтры, `.gitignore`, профили, лимит размера и политику ссылок, что и `scan`. Расширения `.json`, `.yaml`, `.yml`, `.toml` и `.xml` не включены в список по умолчанию: добавь их через `--extension` или настрой `scan.extensions`. Для них без селектора фрагменты не извлекаются.

Поддерживаемые форматы и границы извлечения:

| Формат | Что извлекается | Ограничения |
| --- | --- | --- |
| Rust, C#, C, C++ | Комментарии, documentation comments и строки доказуемых контекстов сообщений | `.h` с одинаково подходящей грамматикой C/C++ помечается `partial`; `header_language` задаёт выбор |
| PowerShell | Комментарии, comment-based help, строки команд сообщений и here-strings | `.psd1` отмечается `unsupported` как data-файл |
| Markdown | Заголовки, абзацы, списки, GFM-таблицы и подписи ссылок | Цитаты и code blocks исключаются; неточное сопоставление даёт `partial` |
| TXT | Непустые строки текста | Структурной разметки нет |
| reStructuredText, AsciiDoc | Заголовки и проза с базовой обработкой директив, ссылок и literal/code blocks | Поддерживается консервативное подмножество разметки |
| JSON, YAML, TOML, XML | Только строковые значения по настроенным селекторам | Расширение нужно включить явно; YAML tags/aliases не интерпретируются, повторяющиеся JSON/YAML-ключи пропускаются, TOML-массивы таблиц (`[[table]]`) помечаются `partial` |

В TOML селекторы задаются по расширению файла. Поддерживается безопасное подмножество путей: свойства через `.name`, ключи через `['name']` или `["name"]`, индексы обычного массива `[0]` и wildcard `*`. YAML flow mappings поддерживаются; повторяющиеся JSON/YAML-ключи в одном объекте/отображении пропускаются с диагностикой, потому что разные потребители могут выбрать разные значения. TOML-массивы таблиц пока пропускаются с диагностикой.

~~~toml
[scan]
extensions = [".rs", ".cs", ".md", ".json", ".yaml"]

[extract]
header_language = "auto" # auto, c или cpp для неоднозначных .h
message_calls = ["MyLogger.ShowMessage", "logger->Notify"]

[extract.selectors]
".json" = ["$.ui.message", "$.errors[*].description"]
".yaml" = ["$.ui.message"]

[profiles.docs]
priority = 5
match_paths = ["docs/**"]
[profiles.docs.extract.selectors]
".json" = ["$.ui.message"]
~~~

В отчёте извлечения схема называется `language-review.extract` и имеет собственную версию `1.0`; она не меняет JSON-схему `scan` версии `1.0`. Документ содержит относительный путь, root ID, выбранный профиль, формат, кодировку, BOM, SHA-256, статус и диагностические коды. Каждый фрагмент включает `text`/`source_text`, вид, контекст, стабильный ID, исходный диапазон и защищённые диапазоны.

`byte_offset` — смещение от начала исходных байтов, включая BOM; `line` и `column` начинаются с 1; `column` считает Unicode code points, tab считается одной колонкой, `utf16_column` считает UTF-16 code units. Конец `range` исключающий. Диапазоны фрагментов указывают на ровно те байты, которые сериализованы как исходный текст; кодированные escape-последовательности остаются в исходном виде и защищаются отдельно.

| Поле координат | Единица | Начало отсчёта |
| --- | --- | --- |
| `byte_offset` | Байты исходного файла в исходной кодировке | 0, включая BOM |
| `line` | Физические строки `LF`, `CRLF` или `CR` | 1 |
| `column` | Unicode code points; tab считается одним | 1 |
| `utf16_column` | UTF-16 code units | 1 |

Документ может иметь статус `extracted`, `skipped`, `unsupported`, `partial` или `error`. В JSON при частичных результатах stdout остаётся корректным JSON, а коды диагностики идут в stderr. `extract` возвращает `3`, если есть `partial`, `unsupported` или `error`, и `2` для ошибочного входного пути или конфигурации.

Полный реальный ответ, полученный командой `extract` на постоянной синтетической фикстуре, хранится в [extract-report.example.json](docs/extract-report.example.json). Его диапазоны, ID и SHA-256 рассчитаны из байтов фикстуры. Поля и ограничения описаны в [JSON Schema](docs/extract-report.schema.json).

### Языковая проверка

~~~powershell
language-review check .\repo
language-review check .\src\main.rs --format json
language-review check .\docs --engine languagetool --engine vale
language-review check .\repo --llm-provider ollama --category spelling --category grammar
language-review check .\repo --format json --output .\check-report.json
~~~

`check` использует тот же выбор файлов, профили и исключения, что `scan` и `extract`, и проверяет только фрагменты `extract`: целые файлы кода и неотобранные значения структурированных файлов движкам не передаются. Настройка `llama-server`, LanguageTool, Vale и Ollama в Windows и WSL2/Linux, фактические параметры производительности и типовые ошибки описаны в [руководстве по движкам](docs/language-engines.md).

Перед отправкой движку фрагмент маскируется: защищённые диапазоны `extract` и технические токены (`id.ToString()`, `snake_case`, флаги CLI, имена файлов, URL) заменяются заглушкой, escape-последовательности, сущности и разметка Markdown показываются своим буквальным значением, CR нормализуется. Соседние строки одного абзаца или комментария проверяются вместе, чтобы не терять контекст предложения. Каждая позиция движка отображается обратно на исходник; позиция внутри маски не угадывается — такое замечание отбраковывается, а правка, задевающая защищённый текст, получает статус `rejected`.

Каждое замечание сохраняет происхождение: документ, `source_sha256`, ID фрагментов, точный диапазон и цитату исходника, а также для каждого движка правило, категорию, сообщение и уверенность модели (у LanguageTool и Vale её нет). Объединение требует одной общей минимальной правки (диапазон и текст) у всех членов группы внутри одной единицы проверки и совместимых категорий. Разные правила одного движка остаются отдельными; пересечения диапазонов и попарных совпадений правок недостаточно. Перечень источников (`agreement`) не превращается в общую «вероятность». Предложения имеют статус `candidate` (прошли проверки границ, отрицаний, технического содержимого и экранирования, но требуют ручной проверки) или `rejected` с причинами.

Статус результата: `clean` — проверено полностью, замечаний нет; `findings` — проверено полностью, замечания есть; `partial` — часть текста не проверена или извлечена неполно; `unavailable` — выбранный движок недоступен или завершился ошибкой; `error` — ошибка входных данных. По каждому движку отчёт содержит статус, версию, модель, число проверенных, пропущенных и сбойных единиц, находок, отбракованных результатов и время.

Отчёт имеет схему `language-review.check` версии `1.0`: [JSON Schema](docs/check-report.schema.json) и [реальный пример](docs/check-report.example.json), построенный командой `check` с LanguageTool 6.6 и Vale 3.24.0 на фикстурах `tests/fixtures/check`. Схемы `scan` и `extract` не меняются.

~~~toml
[check]
engines = ["languagetool", "vale", "llm"]
categories = []                       # пусто — все категории
terms = { "фреймворк" = "каркас" }    # терминология проекта для Vale и LLM

[check.languagetool]
endpoint = "http://127.0.0.1:8081"

[check.llm]
provider = "llama_cpp"                # или "ollama"

[check.llm.llama_cpp]
endpoint = "http://127.0.0.1:8080"

[profiles.docs.check]
engines = ["languagetool", "vale"]
~~~

Профиль может переопределять `engines`, `categories` и `terms`; адреса и параметры движков задаются в основном разделе `[check]`. Нелокальные адреса допускаются только при явном `check.allow_remote_endpoints = true`.

Каталоги зависимостей и сборки, в том числе `.git`, `.venv`, `node_modules`, `target`, `bin`, `obj`, `build` и `dist`, исключаются по умолчанию. Для пользовательских исключений используй `--exclude 'docs/generated/**'`. Также поддерживаются `.gitignore` и отрицательные правила Git; обход ссылок выключен по умолчанию. `--follow-symlinks` включает ссылки только в пределах явно указанного корня и защищает от циклов.

Для стандартной конфигурации выбирай проектный профиль по маркерам, заданным в пользовательском конфиге; `--profile NAME` выбирает профиль явно. Профили с `match_paths` могут задавать настройки для относительных путей внутри корня сканирования.

### Диагностика

~~~powershell
language-review doctor
language-review doctor .\src
language-review doctor --format json
~~~

`doctor` проверяет установленный пакет, версию Python, загруженную конфигурацию, заданные пути, программы из `doctor.programs`, доступность HTTP-сервисов на локальном компьютере из `doctor.http_services` и готовность языковых движков из `check.engines` (модель, версия, адрес без секретов). Недоступность необязательной программы или движка не мешает `scan`, но отражается в результате диагностики и коде завершения.

### Конфигурация

~~~powershell
language-review config show
language-review config show --format json
language-review --config .\language-review.toml scan .\repo
~~~

Пользовательский конфиг хранится в `%APPDATA%\language-review\config.toml` на Windows и в `$XDG_CONFIG_HOME/language-review/config.toml` (или `~/.config/language-review/config.toml`) на Unix. Явно переданный `--config` объединяется поверх пользовательского файла; параметры CLI имеют наивысший приоритет. Значения `config show` сопровождаются источником. Поля, похожие на секреты, и параметры URL скрываются.

Пример TOML:

~~~toml
[scan]
respect_gitignore = true
max_file_size = 5000000
exclude_patterns = ["docs/generated/**"]

[doctor]
programs = ["vale"]
http_services = { ollama = "http://127.0.0.1:11434/api/tags" }

[profiles.rust]
priority = 20
project_markers = ["Cargo.toml"]
match_paths = ["crates/**"]
[profiles.rust.scan]
extensions = [".rs", ".md", ".txt"]
~~~

## Коды завершения

- `0` — команда выполнена; пропуски являются ожидаемым результатом инвентаризации; для `check` — замечаний нет.
- `1` — только `check`: проверка полная, найдены замечания.
- `2` — неверные аргументы, отсутствующий входной путь или ошибочная конфигурация.
- `3` — ошибка чтения/обхода, недоступный настроенный сервис или программа, неразрешимый указанный путь либо неполное/неподдерживаемое извлечение; для `check` — ошибка сохранения отчёта.
- `4` — только `check`: проверка неполная (частичное извлечение, непроверенные фрагменты); найденные замечания сохраняются в отчёте.
- `5` — только `check`: выбранный движок недоступен или завершился ошибкой.
- `130` — операция прервана пользователем.

Коды `scan`, `extract`, `doctor` и `config show` не изменились.

## Проверки разработки

Python-исходники, тесты и документация находятся в проекте. Временные окружения и результаты сборки не входят в исходники.

Порядок команд и критерии проверки собраны в [контексте проверок](.codex/context/verification.md). Скрипт `scripts/verify-package.ps1` собирает wheel и sdist, устанавливает их в отдельные временные среды и проверяет установленные точки входа, `python -m language_review`, `scan`, `extract` и `check` со встроенными правилами Vale (или явный статус `unavailable` без Vale). Приёмочные тесты на реальных движках описаны в [руководстве по движкам](docs/language-engines.md#приёмочные-проверки-на-реальных-движках).

## Границы поддержки

`scan` остаётся инвентаризацией и сохраняет свою схему. `extract` не вызывает языковые движки и не предлагает исправления. `check` не изменяет исходники и не объявляет предложения LLM или словаря безопасными: это гипотезы для независимого решения агента. Качество LLM ограничено: модель пропускает ошибки и может предлагать замены, меняющие смысл, поэтому замены с изменением отрицаний или технического содержимого отклоняются. Tree-sitter грамматики поставляются как обычные runtime-зависимости и не скачиваются во время анализа. Markdown поддерживает заголовки, абзацы, списки, GFM-таблицы, подписи ссылок и inline-разметку; неоднозначное сопоставление с исходником помечается как частичный результат.
