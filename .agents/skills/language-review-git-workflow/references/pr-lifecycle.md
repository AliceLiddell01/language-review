# Публикация без потери пользовательских изменений

1. Выполни `git status`, `git branch --show-current`, `git remote -v`, `git fetch` и получи SHA основной ветки и base. При работе только через API проверяй ожидаемый SHA сравнением.
2. Проверь, кому принадлежат текущие изменения; неизвестные изменения сначала классифицируй, не удаляй их.
3. Создавай новую ветку от актуальной основной ветки только для новой задачи. Для продолжения PR используй его head и сравни с реальной удалённой веткой.
4. Запусти применимые проверки: `git diff --check`, проверку `.gitignore` и отсутствие токенов или больших фрагментов пользовательских текстов.
5. Добавь в индекс только нужные файлы, изучи `git diff --cached --stat` и `git diff --cached --check`, создай commit с предметным сообщением.
6. Выполни обычный push. Сверь SHA из `git rev-parse HEAD` и `git ls-remote <remote> refs/heads/<branch>`; они должны совпасть. Через GitHub API сравни `refs/heads/<branch>` с созданным commit.
7. Создай или обнови **один** PR в фактическую base-ветку; актуализируй описание по [pr-body.md](pr-body.md), перечитай head/base/body после записи.
8. После нового commit предыдущие результаты CI и ревью устаревают: проверь последние проверки. Меняй состояние Draft/Ready только при выполнении соответствующих условий.
9. Выполняй merge только по отдельному поручению. После него сравни merged SHA; очищай рабочую среду только при отдельном разрешении.

Из-за ограничений внешнего сервиса не считай неполный вывод CLI, отсутствие доступа или таймаут подтверждением успешного push/PR.
