# Независимая оценка и регрессии

`language-review-eval` оценивает сохранённую фактическую выдачу `check`/`review` 1.0.
Офлайн-команды не загружают движки, не обращаются к сети и не меняют исходники.
Эквивалентная точка входа: `python -m language_review.evaluation`.
Обнаружение ошибок и существующие контракты продукта не изменены.

## Граница доказательств

В Git находится **синтетический контроль контрактов**, а не независимый baseline
русского технического письма. [Корпус](../tests/fixtures/evaluation/corpus.json) содержит
17 авторских примеров: 15 dev, один validation и один замороженный test. Права на эти
специально созданные материалы разрешают публикацию. Метки `synthetic_contract` проверяют
арифметику и сценарии; они не становятся человеческим языковым эталоном.

[Сохранённый review](../tests/fixtures/evaluation/report.json) получен настоящим публичным
`check --engine vale --view review` на Vale 3.24.0, без подделки структуры отчёта.
[Русский отчёт](../tests/fixtures/evaluation/report.ru.md) и
[ожидания](../tests/fixtures/evaluation/expectations.json) построены оценщиком.
Результат `PARTIAL` намеренный: короткий английский текст и английское сообщение не
проверены русскими правилами Vale, PowerShell-комментарий извлечён частично, один
стилистический случай спорный. Это потери покрытия, а не чистые случаи.

**Независимая приёмка на реальных данных: NOT_RUN.** Вместе с задачей не предоставлены
разрешённые реальные исходники с независимой исчерпывающей разметкой. Для завершения
исследования нужны: конкретная версия технического корпуса и разрешение его использовать;
независимый эксперт, подтверждающий ошибки и чистые случаи; решение разногласий;
репозитории/семейства исходников, разнесённые по split; заморозка test; выбранные
доступные движки. Оценщик не заменяет эти действия собственными суждениями.

`report_kind` выводится из данных:

| Тип | Условие и назначение |
| --- | --- |
| `synthetic_contract_check` | Все выбранные данные синтетические; только проверка механизма |
| `independent_baseline` | Все выбранные данные реальные, применимые, исчерпывающе и независимо подтверждённые |
| `exploratory` | Смешанные данные или неподтверждённая разметка; без заявлений об общей точности |

`PASS` означает, что применимая оценка выполнена полностью, а не высокую точность.
`PARTIAL` сохраняет известные находки и показывает недостающие проверки.
`NOT_RUN` означает отсутствие оцениваемой разметки, выбранных случаев либо фактически
проверенного текста. Код CLI: 0 — полная оценка/валидный импорт; 4 — неполная оценка
или NOT_RUN; 2 — неверный контракт/вход; 3 — ошибка записи/доступа; 1 — нарушены
регрессионные ожидания; 130 — прерывание. `compare` с регрессией возвращает 0:
это описание различий, а не универсальный quality gate.

## Офлайн-воспроизведение в PowerShell

Каждый `--output` должен быть новым файлом или каталогом. Перезапись запрещена,
включая попытку заменить корпус или исходный отчёт.

```powershell
$work = Join-Path $env:TEMP ('lr-evaluation-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $work | Out-Null
$corpus = 'tests/fixtures/evaluation/corpus.json'
$saved = 'tests/fixtures/evaluation/report.json'
uv run --locked language-review-eval validate $corpus
uv run --locked language-review-eval score $corpus $saved --split dev `
  --bind root-0001=demo --format json --output (Join-Path $work 'baseline.json')
# Ожидается код 4: контрольная фикстура намеренно PARTIAL.
uv run --locked language-review-eval regress (Join-Path $work 'baseline.json') `
  tests/fixtures/evaluation/expectations.json
uv run --locked python -m language_review.evaluation score $corpus $saved `
  --split dev --bind root-0001=demo --output (Join-Path $work 'report.md')
uv run --locked language-review-eval compare (Join-Path $work 'baseline.json') `
  (Join-Path $work 'baseline.json') --format json
```

Импорт проверяет JSON Schema, версию, уникальность ID, связи review/analysis/evidence,
систему координат и сопоставление root с **явно указанным** репозиторием корпуса.
Документ определяется парой repository/path и SHA-256 исходных байтов, а не нестабильным
ID. Присутствующий документ с чужим хешем отклоняется; отсутствующий становится неполным.
Документы отчёта вне корпуса не участвуют в метриках. Кандидаты вне размеченных случаев
считаются в `ignored_outside_annotated_cases`, а не объявляются FP.

Все диапазоны сверяются существующим `SourceMap`/проверкой точной цитаты: байты включают
BOM, строки и Unicode-столбцы начинаются с 1, конец исключающий, `utf16_column` отдельный.
Нельзя «починить» диапазон поиском похожей цитаты. Корпус хранит оригинальные байты в
base64: CRLF, BOM и UTF-16 не меняются при переносе JSON через Git.

## Формат корпуса и ручная разметка

Источник контракта — [corpus.schema.json](../src/language_review/evaluation/schemas/corpus.schema.json).
`validate` проверяет также межобъектные инварианты, хеши, координаты, split и freeze.
`export` выполняет канонический импорт/экспорт JSON без потерь и изменения байтов источника.
Хеши corpus/report/judgments считаются по каноническому JSON оценщика (UTF-8, sort_keys,
indent=2, завершающий LF), поэтому пробелы и порядок ключей не меняют смысловой отпечаток.
SHA-256 исходников и переданного TOML-конфига, напротив, считается по исходным байтам.

Создание **черновика** из файла, права на использование которого уже получены:

```powershell
uv run --locked language-review-eval init C:/corpora/allowed/sample.rs `
  --repository approved-repo --path src/sample.rs --origin 'source reference, revision' `
  --rights-basis 'permission reference' --data-kind real --publish private_only `
  --output (Join-Path $work 'draft.json')
uv run --locked language-review-eval export (Join-Path $work 'draft.json') `
  --output (Join-Path $work 'annotation-copy.json')
```

`init` не назначает метки: `draft`, `disputed`, `exhaustive=false`. Вручную разбейте файл
на непересекающиеся **ожидаемые фрагменты**, включая не извлекаемые продуктом места.
Диапазон случая должен описывать целевой текст, а не весь код с синтаксисом. Иначе
покрытие справедливо покажет неполное извлечение. `protected_ranges` задаёт машинные
вставки, не требующие языковой проверки; они исключаются из проверки покрытия символов.
Каждая документная запись хранит repository, относительный path, revision, origin,
права use/publish/basis, тип данных, кодировку, BOM, SHA-256 и исходные байты.
Частные origin/evidence и содержимое private_only остаются вне публичного Git.

Случай содержит контекст `documentation/comment/message/log/other`, profile, languages,
применимые категории, допустимые terms и exceptions. Эти сведения — ожидания разметки;
они не подменяют конфигурацию анализаторов автоматически. Настройте профиль продукта
отдельно; его фактически применённые параметры сохраняются в манифесте.

Правила независимой разметки:

1. Эксперт читает оригинальный текст с назначением и техническим контекстом **до просмотра
   выдачи продукта**. Настоящая ошибка нарушает проверяемую норму/согласованный контракт;
   предпочтение другой формулировки само по себе ошибкой не является.
2. Отдельно помечаются орфография, грамматика, пунктуация, стиль, терминология и
   `untranslated_english`. Терминологическая ошибка требует конкретного словаря/политики.
   Для английской документации и разрешённых API/CLI терминов перевод не обязателен.
   Деловой стиль, аббревиатуры, отрицания, идентификаторы и логи могут быть корректными.
3. Для ошибки создаются постоянный label ID, точные `anchors`, категория и необходимый
   контекст. `anchors` — заранее подтверждённые альтернативные области одного диагноза;
   не добавляйте их автоматически из предсказаний. `corrections` хранит несколько правок
   `{range,text}`. Пустой список означает: ошибка известна, безусловная замена не установлена.
   Возможны нулевые диапазоны для вставки знака пунктуации.
4. Чистый фрагмент получает `verdict=clean`, `labels=[]` и подтверждение эксперта.
   `exhaustive=true` означает, что эксперт просмотрел весь случай на указанные категории,
   включая отсутствие других ошибок. Непросмотренный фрагмент нельзя назвать чистым.
5. Каждое подтверждение, в том числе чистого случая, хранит actor (допустим псевдоним),
   method, evidence и history с revision/actor/decision. Модельные предложения остаются
   `draft`; реальные independently_verified метки допускают только human/external_reference.
   Формат проверяет декларацию происхождения, а не удостоверяет личность эксперта.
6. Второй аннотатор работает независимо. `agreement first.json second.json` выводит n
   пар разных actor, точное согласие целых случаев и конфликтные ID. Это не Cohen kappa:
   шанс-согласие не оценивается. Разное разбиение на случаи отвергается. Один actor
   не образует независимую пару. Непарные случаи показаны отдельно.
   Модельное/pipeline происхождение любой из сравниваемых меток исключает пару из
   независимого согласия; исключённые case ID перечислены в отчёте.
7. Конфликты остаются disputed до решения третьего эксперта с обоснованием в history.
   Меняются annotation_version и corpus version; оба сравниваемых отчёта пересчитываются.
   Оценщик не выбирает истину голосованием и не подтверждает собственные выходы.

## Разбиение и отложенный тест

`split_policy` фиксирует стратегию и правила доступа к ответам. repository должен
обозначать каноническое семейство происхождения, включая forks и копии одного проекта.
Валидатор запрещает пересечение repository между split, одинаковые байты документа,
нормализованные дубли случаев, включение текста длиной от 20 символов друг в друга и
Jaccard >= 0.8 по нормализованным символьным 5-граммам. Для коротких текстов сравнивается
точная нормализованная строка. Это консервативный фильтр; перефразированные дубли и
скрытое общее происхождение требуют ручного аудита до заморозки.

`freeze-test corpus.json --output frozen.json` записывает SHA-256 всех test-случаев и
их документов; изменение меток, контекста или байтов test после этого отклоняется.
`materialize ... --split test --output NEW_DIRECTORY` выдаёт только байты выбранного
split, без ответов. Доступ к самому JSON с test-метками должен иметь только оценщик/эксперт;
формат не является системой разграничения доступа. Не загружайте этот JSON в будущие
промпты, retrieval или память разработки. Настройка правил на test требует новой версии
и нового отложенного набора, а не заявления о независимом результате на старом.

## Matching и метрики

В основном эталоне участвуют только applicable/exhaustive случаи с подтверждённой
разметкой всех меток. Draft/disputed/неприменимые случаи — `not_evaluated`.
Для каждого уровня (финальный pipeline и каждый движок) matching выполняется отдельно.
Категория кандидата вне независимо размеченного `case.categories` получает
`not_evaluated`, а не FP. Чистота и TN относятся только к размеченной области категорий.

| Решение | Правило |
| --- | --- |
| TP detection | Одинаковые документ, точный полный anchor и категория; одна ещё не закрытая метка |
| FP | Локализованный кандидат в исчерпывающе размеченном случае без соответствующей ошибки, включая лишний дубликат и неверную категорию |
| FN | Подтверждённая ошибка без кандидата; в pipeline также потери до/после движков |
| needs_adjudication | Та же категория с пересекающимся, но не точным диапазоном; несколько возможных меток; правка с конфликтующими альтернативами |
| TN | Полностью проверенный подтверждённый чистый случай без кандидатов; единица TN — случай, не токен |

Совпадения цитаты, ID, agreement или priority не используются как доказательство.
Кандидаты сортируются по стабильному хешу диапазона/категории/правок; одинаковый диагноз
может закрыть метку один раз. Дополнительное замечание не создаёт второй TP. Выбор
между дублями не зависит от правильности предложенной замены. Неразрешённые gold-связи
выводятся в `unresolved_gold`, исключаются из TP/FN и сопровождаются `PARTIAL`.
Если кандидат касается нескольких случаев, он относится к первому случаю в порядке
корпуса; выход за его границу требует adjudication и не создаёт TP в соседнем случае.

Для correction сравниваются исходные байты после одной предложенной правки с байтами
после каждой разрешённой эталонной правки. Это допускает разные минимальные диапазоны
одного и того же результата. `correct` требует, чтобы **все** опубликованные применимые
варианты данного замечания совпадали с эталоном; смесь совпавших/несовпавших вариантов
требует adjudication. `incorrect` здесь означает несовпадение с зафиксированными
вариантами, а не автоматическое доказательство смыслового вреда. При отсутствии
эталонной замены — `unknown`, при отсутствии candidate-правки — `absent`.
Отбракованные правки не считаются предложенными финальными исправлениями.

`detection` считает только полностью проверенные применимые случаи.
`pipeline_detection` включает все подтверждённые применимые случаи: отсутствующий
документ, отключённая категория или недоступный движок сохраняют FN, даже если условная
полнота на проверенной части выглядит высокой. `correction` использует полный pipeline:
TP — правильно исправленные метки, FP — неверные предложения, FN — метки с известной
правкой, которые не получили правильной коррекции. Эти знаменатели не смешиваются.

Формулы: P=TP/(TP+FP), R=TP/(TP+FN), F1=2TP/(2TP+FP+FN),
F0.5=1.25TP/(1.25TP+FP+0.25FN). Все целые счётчики и знаменатели сохранены;
нулевой знаменатель даёт null и причину в undefined. FP/1000 использует **только FP
полностью оценённых применимых случаев**, делённые на число таких случаев.
`overediting` отдельно считает style/bureaucratese/terminology FP на чистом тексте.

Разрезы category/format/context/data_kind и таблицы каждого движка содержат n.
Их малые группы не позволяют судить о генеральной совокупности; доверительные интервалы
не вычисляются. Уникальный вклад движка — множество меток, правильно найденных им в
финальном pipeline и не найденных другими; shared — пересечение. Две гипотезы одного
движка не становятся независимыми голосами. Retained sources, final findings,
filtered и unlocalized/rejected учитываются отдельно.

## Покрытие и ограничения диагностик

`coverage` показывает наблюдаемые документы, извлечённые случаи, применимость, проверку,
число фрагментов, непросмотренные символы и статусы движков.
`checked` означает хотя бы одну фактическую проверку движком, `fully_checked` —
проверку всеми выбранными применимыми движками. Сбой другого движка не обнуляет
индивидуальные метрики здорового анализатора. Проверка покрытия допускает
только пробелы и явно защищённые вставки вне извлечённых диапазонов. При partial extraction,
сбое документа, пропусках выбранных движков, отключённых категориях и rejected-выдаче
случай остаётся неполным. Пустые configuration.categories в check означают **все категории**.

Причины `before:*`, `routing_or_engine:*`, `after:rejected:*` отделяют наблюдаемые стадии.
Check 1.0 не содержит полного списка просмотренных/выбранных scan-файлов: различить
«не обошли» и «не выбрали» для отсутствующего документа нельзя. Эти числа не выдумываются.
Review дополнительно сохраняет filtered/unlocalized и исходные evidence; rejected
цитаты без надёжного исходного диапазона не локализуются приблизительно и не получают TP.
Per-engine метрики относятся к локализованным сохранённым sources; это не обещание
оценить все несохранённые сырые ответы. Числа requests/failures/units/tokens/elapsed и
доступные версии движков берутся из отчёта. Wall-clock берётся из capture-манифеста;
при его отсутствии null. Повторы транспорта, RAM/GPU и деньги без данных — null.

Для смыслового ущерба поддержан отдельный
[judgments-контракт](../src/language_review/evaluation/schemas/judgments.schema.json).
`score --judgments judgments.json` принимает **независимые человеческие** решения,
привязанные к точным corpus/report SHA-256 и стабильному candidate key из evaluation JSON.
Запись содержит case, engine (null для pipeline), candidate, detection, label, correction,
harm (`meaning`, `negation`, `technical_tokens`) и annotation с основанием/историей.
Нельзя назначить два TP одной метке или подтверждать решения методом model/pipeline.
Ручное решение действует только на указанный уровень, без автоматического переноса на
движки. Незаполненный harm остаётся неоценённым; risk причины продукта — только сигналы.
Сравнение reference_only с independent_judgments отклоняется как разные протоколы.

## Live capture, манифест и повторы

```powershell
$head = (git rev-parse HEAD).Trim()
uv run --locked language-review-eval run $corpus --split dev --engine vale `
  --product-commit $head --output (Join-Path $work 'live-vale')
# Только если эти выбранные сервисы реально доступны и уже настроены:
uv run --locked language-review-eval run $corpus --split dev `
  --engine languagetool --engine vale --engine llm --config C:/corpora/engines.local.toml `
  --product-commit $head --repeat 3 --output (Join-Path $work 'repeated')
```

`run` материализует только исходные байты split во временном каталоге и запускает
**публичный** `python -m language_review check --view review`. Конфигурация и промпты
не получают метки. Отчёты пишутся отдельно от входов; хеши входов сверяются после запуска.
Манифест сохраняет корпус/split/report/config SHA-256, заявленный точный product commit,
код выхода, wall-clock, номер повтора и параметры CLI. Оценка также хранит версию
продукта/оценщика/метрик/схемы, действующие конфигурации документов и engine details,
включая model, prompt version/hash, seed/thinking/ограничения, когда продукт их сообщил.
SHA программы задаётся оператором проверенной установки; манифест не удостоверяет
подлинность бинарника. У старого saved report commit/config hash могут быть неизвестны:
это явно отмечено в missing_provenance.

Недоступный сервер не заменяется другим. Его публичный статус сохраняется в review и
оценке; timeout/ошибка без пригодного JSON создаёт not-run запись. `distribution.json`
содержит статусы, n, исходные значения, min/max/mean P/R/F1/F0.5 для повторов. Это
описательное распределение, не доказательство устойчивости LLM и не доверительный интервал.
`aggregate result1.json result2.json ...` повторяет агрегацию offline.
Одно измерение не получает заявления об устойчивости. Серверы и модели не запускаются,
не устанавливаются и не заменяются этой командой.

## Сравнение и долговременные ожидания

`compare baseline.json candidate.json` проверяет совпадение хеша и версий корпуса/разметки,
split, metric/scorer version, report_kind и judgment_policy. Конфигурации анализаторов
могут отличаться — это предмет сравнения. Несовместимые входы отклоняются.
Результат содержит новые/удалённые FP, новые/восстановленные FN, новые/потерянные и
изменившиеся TP, дельты метрик/разрезов/движков, изменения покрытия каждого case и затрат.
Постоянные ключи — case/label и хеш кандидата; find-ID продукта не участвует.

`regress result.json expectations.json --record` создаёт новый зафиксированный SHA
детерминированной проекции; без --record проверяет её и возвращает 1 при изменении.
Из проекции исключены capture-происхождение и тайминги. Ожидания предназначены для
пересчёта **сохранённого** отчёта: нельзя использовать их как требование идентичного
ответа живой LLM. Перед намеренной сменой ожиданий изучите `compare` и изменённые кейсы.
Схемы [result](../src/language_review/evaluation/schemas/result.schema.json),
[run](../src/language_review/evaluation/schemas/run.schema.json),
[expectations](../src/language_review/evaluation/schemas/expectations.schema.json)
упакованы вместе с оценщиком; offline не загружает remote $ref.

## Приёмочные доказательства и исследовательские ориентиры

Детерминированные проверки — `tests/test_evaluation.py` и
`tests/test_evaluation_workflows.py`. Их HTTP-фикстуры — синтетические ответы протокола,
которые проходят через настоящий check; они не доказывают языковую точность движков.
Windows wheel/sdist smoke выполняет validate/score/regress/compare и проверяет сохранность
исходников, корпуса и сохранённого отчёта. Команды всех проверок принадлежат
[verification.md](../.codex/context/verification.md).

Первичные источники проверены при разработке:

- [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
  и [Evaluation flywheel](https://github.com/openai/openai-cookbook/blob/main/examples/evaluation/Building_resilient_prompts_using_an_evaluation_flywheel.md)
  поддерживают предметные evals, независимую экспертную оценку и отдельный test. Их общие
  принципы применимы к техническому русскому, но готового русского эталона они не дают.
- [ERRANT](https://github.com/chrisjbryant/errant) служит ориентиром разделения detection/
  correction и F0.5. Штатный annotator принимает английский; это не готовый русский scorer.
  Он не добавлен в зависимости; совместимость его NLP-стека с Python 3.15 не заявляется.
- [RULEC-GEC](https://github.com/arozovskaya/RULEC-GEC) требует User Agreement для получения
  разметки. Это русский учащихся в академических текстах; перенос чисел на комментарии
  к коду, логи и CLI без отдельной доменной проверки необоснован. Данные не скачивались.
- [Работа о reference-less GEC](https://aclanthology.org/2021.emnlp-main.239/) описывает
  проблему разнообразных правильных переформулировок. Здесь предусмотрены альтернативы
  и ручное решение; reference-less judge и его перенос на русский не реализованы.

Новые NLP/evaluation-зависимости и удалённые сервисы оценщику не потребовались.
