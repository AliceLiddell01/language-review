# Публикация без потери пользовательских изменений

1. `git status`, `git branch --show-current`, `git remote -v`, `git fetch` и получение default/base SHA. У remote-only API используй защищённое сравнение ожидаемого SHA.
2. Проверь принадлежность текущих изменений; при неизвестных изменениях остановись на их классификации вместо их удаления.
3. Новую ветку делай от актуального main/default только для новой задачи. Для продолжения существующего PR используй его head и сопоставь с реальным remote.
4. Запусти применимые проверки; `git diff --check`, проверка `.gitignore` и отсутствие токенов/массивов пользовательских текстов.
5. Stage точные файлы, `git diff --cached --stat`, `git diff --cached --check`, commit с предметным сообщением.
6. Push обычным способом. Проверь SHA `git rev-parse HEAD` и `git ls-remote <remote> refs/heads/<branch>`; значения должны совпасть. Для GitHub API — сравни `refs/heads/<branch>` с созданным commit.
7. Создай/обнови **один** PR в реальный base; актуализируй body по [pr-body.md](pr-body.md), перечитай head/base/body после записи.
8. После нового commit предыдущие CI/review results устарели: проверь latest checks. Переводи Draft/Ready только если соответствуют указанным условиям.
9. Merge выполняй исключительно по отдельному поручению. После него сравни merged SHA и работай с cleanup только при разрешении.

Из-за ограничений внешнего провайдера не трактуй неполный CLI output, отсутствие доступа или таймаут как успешный push/PR.
