# Семантика консолидации памяти

Одна задача очереди относится к конкретной находке `c1`. До 16 родственных находок
(`c2` и далее) дают модели контекст, но их большинство не подтверждает утверждение
о `c1`. Ответ должен описывать только закономерность, применимую к текущей находке;
если надёжного правила нет, корректен `rules: []`.

## Выбор результата

Консолидация проверяет весь JSON-ответ по Schema, затем проверяет каждое правило:
алиасы свидетельств должны быть выданы этому запросу, категория должна совпадать с
категорией `c1`, текст должен пройти `sanitize` и проверку непустоты. Эти проверки
выполняются также для правила, которое не содержит `c1`. Любая ошибка остаётся
защитным отказом всего ответа. Проверка не смягчает требования к Schema, aliases,
категории или безопасному тексту.

После проверок правило сохраняется лишь тогда, когда в его собственном поле
`evidence` модель явно указала `c1`. Worker не добавляет это свидетельство сам.
Правила без `c1` пропускаются как не относящиеся к текущей задаче; они не вызывают
повтор задания и не публикуются. `rule_selection` в результате и на этапе
`post_schema` содержит числа `received`, `selected` и
`excluded_current_evidence_missing`; они должны удовлетворять равенству
`received = selected + excluded_current_evidence_missing`. Все числа ограничены
размером ответа Schema (не более четырёх правил). `rules` в результате обозначает
число сохранённых правил, в том числе ноль. Пропуск не меняет `subreason` ошибки.
При устаревшей ревизии `selected` отражает предварительный отбор, а `rules: 0`
и `stale: true` подтверждают отсутствие публикации.

При ответе с одним правилом для `{c1}` и другим для `{c2,…,c17}` сохраняется первое,
если оно прошло проверки; второе исключается. Новое правило содержит ровно
свидетельства, которые модель указала, включая `c1`; свидетельства исключённого
правила не переносятся в него. При продолжении lineage сохраняются также прежние
свидетельства вне текущего окна контекста по существующему контракту преемственности.
Если все правила пропущены, задание завершается без новой гипотезы.
Публикация оставшихся правил выполняется существующей транзакцией после повторной
проверки владения lease и ревизий. Канонические события и решения не меняются,
а текущие правила продолжают lineage только по существующим правилам общего
свидетельства, категории и relation.

## Почему выбрана такая обработка

Уточнение промпта с требованием создавать только правила для `c1` полезно как
указание модели, однако само по себе оставляет воспроизведённый конфликт: отдельное
правило только для родственников может по-прежнему привести к отказу всего ответа
и бесполезному повтору. Гранулярный отбор устраняет эту потерю допустимого правила
`c1` и завершает выбор явно. Отбрасывать весь ответ по причине одного правила без
`c1` теряло бы допустимый результат; принимать его, приписав `c1`, создавало бы
фиктивное свидетельство. Отдельный отбор сохраняет границу evidence и текущего
задания.

Статусы `accepted`, `rejected` и `disputed` остаются решениями человека. Модель не
определяет их голосованием. Сохранённое правило — производная гипотеза, не канон;
поиск не использует гипотезы автоматически как норму.

## Синтетический эталон и смысловые ограничения

Ниже зафиксированы искусственные факты и ожидаемые результаты для проверки решения.
Рубрика задана до любых новых вызовов модели. Это локальный синтетический эталон,
полезный для проверки контракта и регрессионных фикстур; он не является human gold
или количественной оценкой качества модели.

`pattern` означает повторяемую форму, подтверждённую конкретными свидетельствами;
`terminology` — точное название или предпочтительный термин с ограниченной областью;
`exception` — явно ограниченное отступление со своими положительными свидетельствами.
Одна категория или большинство похожих случаев сами по себе не подтверждают ни
relation, ни обобщение. Спорное решение не разрешается подсчётом голосов.

| Сценарий и независимые факты | Ожидание для `c1` |
| --- | --- |
| `c1`: защищённое имя команды `lr-migrate`; предложенное в ревью переименование отклонено. Родственные случаи содержат принятые языковые правки в описаниях команды. | Допустима только точная проектная терминология для имени из `c1`, если она нужна для него; принятые правки описаний не обосновывают общее правило переименования. |
| `c1`: двусмысленная фраза, решение `disputed`. Большинство родственных формулировок с `accepted`. | `rules: []`; большинство не разрешает спорный случай. |
| `c1`: обычная проза с подтверждённой опечаткой `инициализирвоать`, решение `accepted`, верная форма `инициализировать`. Родственные случаи о намеренно иных именах команд имеют `rejected`. | Допустимо узкое правило об этой опечатке, опирающееся на `c1`; исключения для имён команд не отменяют исправление и не обосновывают правило для всех идентификаторов. |
| `c1` и соседи отличаются контекстом, и эталонные факты не задают общей языковой нормы. | `rules: []`. |
| Ответ разделяет правило `{c1}` о конкретном термине и правило `{c2,…,c17}` о принятом большинством формате. Второй формат не встречается и не следует из `c1`. | Сохранить первое правило с указанным моделью `c1`; исключить второе, записав счётчик исключений. Не дописывать алиасы. |
| Текст и relation проходят формальную Schema, но предлагают исправление, противоречащее эталонному решению, либо делают широкое обобщение, не подтверждённое примерами. | По рубрике такое правило содержательно не оправдано и не должно считаться подтверждённым. Текущая проверка свободного текста не умеет надёжно распознать этот дефект, даже если модель указала `c1`. |

Последний сценарий задаёт важную границу: наличие настоящего `c1` в `evidence` доказывает
только то, что модель перечислила текущую находку; это не доказывает, что текст правила
логически следует из неё. Текущая Schema и `post_schema` не являются семантическим
оценщиком. Поэтому механический PASS подтверждает только исполнение контракта и
сохранение указанных evidence. Семантическое качество гипотез реальной модели остаётся
`UNKNOWN`: доступной human gold и независимо откалиброванной внешней разметки нет.
Промпт не служит доказательством качества вывода.

Гипотезы остаются необязательными для recall и требуют человеческой проверки перед
принятием решений. Если конкретное обобщение не обосновано, безопасный результат для
него — отсутствие публикации, включая `rules: []`; исправление группировки не даёт
общей гарантии против ложного текста модели.

Это ограничение воспроизводится детерминированным тестом
`test_c1_membership_does_not_prove_semantic_support`: заведомо чрезмерное глобальное
обобщение с `evidence: ["c1"]` сохраняется как гипотеза и доступно при явном
`include_hypotheses=True`. Проход этого теста фиксирует существующий дефект
смыслового принятия, а не доказывает корректность текста. Полный запрет публикации
неподтверждённых обобщений остаётся невыполненным; механический отбор не закрывает
этот критерий. Для него нужна независимая проверка смысла либо отдельное решение
не публиковать свободный текст модели.
