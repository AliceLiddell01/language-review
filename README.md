# Language Review

Language Review — локальная CLI-утилита для языковой проверки русского технического текста в исходниках и документации. Она помогает разработчикам и редакторам найти комментарии, сообщения и прозу, проверить их выбранными движками и вернуться к точному месту в исходном файле.

Работа строится в три шага: **`scan` → `extract` → `check`**. Каждый шаг можно запустить отдельно: получить список файлов, изучить извлечённый текст или сразу выполнить языковую проверку. Результат — текстовый или JSON-отчёт с происхождением замечаний; исправления требуют ручного решения и не применяются программой.

## Быстрый старт

Поддерживаемая среда разработки и приёмки — **Windows и PowerShell**. Нужны Git, Python **3.15 или новее** (в `.python-version` закреплён 3.15.0) и uv **0.13.1 или новее**. Версии зависимостей зафиксированы в `uv.lock`.

Для сборки `tree-sitter` из исходников на Windows с закреплённым Python 3.15 нужны Visual Studio Build Tools с компилятором MSVC и компонентами C++: в текущем lock-файле для этой зависимости нет Windows wheel. Грамматики Tree-sitter устанавливаются с пакетом и не скачиваются во время анализа.

Установка из репозитория и первый запуск без языковых сервисов, OAuth и Docker:

```powershell
git clone https://github.com/AliceLiddell01/language-review.git
Set-Location language-review
uv sync --locked
uv run --locked language-review --version
uv run --locked language-review scan .\README.md
uv run --locked language-review extract .\README.md
```

`scan` покажет тип файла, кодировку/BOM, переводы строк, размер и читаемость. `extract` покажет человекочитаемые фрагменты и их диапазоны. Эти команды не выполняют языковую проверку. В клоне уже есть проектная конфигурация.

Для своего репозитория сначала создайте её явно. Замените `..\repo` на путь к существующему целевому репозиторию:

```powershell
uv run --locked language-review init ..\repo
uv run --locked language-review config validate ..\repo
uv run --locked language-review scan ..\repo
uv run --locked language-review extract ..\repo
```

`init` создаёт `.language-review.yaml` в корне цели и не перезаписывает существующий файл. Если он уже есть, начните с `config validate`. Без этого файла `scan`, `extract` и `check` завершаются с кодом `2`. Правила корней Git/worktree и каталогов вне Git описаны в [руководстве по конфигурации](docs/project-configuration.md#корень-и-пути).

Все примеры ниже выполняются из каталога Language Review через `uv run --locked`. После активации `.venv\Scripts\Activate.ps1` можно вызывать `language-review` напрямую. Доступны также `uv run --locked language-review --help` и `uv run --locked python -m language_review --version`.

## Типичные сценарии

### Изучить файлы и сохранить извлечённый текст

```powershell
uv run --locked language-review scan ..\repo --format json --output ..\scan-report.json
uv run --locked language-review extract ..\repo --format json --output ..\extract-report.json
```

Отчёты в этих примерах сохраняются вне исследуемого каталога. Без `--output` результат идёт в stdout; при `--format json` это только JSON, а диагностика идёт в stderr. Формат по умолчанию — человекочитаемый.

Все три команды учитывают профили, `.gitignore`, исключения и лимит размера. Каталоги `.git`, `.venv`, `node_modules`, `target`, `bin`, `obj`, `build` и `dist` исключены по умолчанию. `--exclude 'docs/generated/**'` добавляет исключение, `--extension .json` — расширение, а `--only-extension .md` заменяет список расширений. Обход символических ссылок выключен; `--follow-symlinks` разрешает только ссылки внутри явно указанного корня с защитой от циклов. Вложенные Git-репозитории передавайте отдельными целями с собственной конфигурацией.

### Проверить язык выбранными движками

Сначала установите и настройте нужные движки по [руководству](docs/language-engines.md). `uv sync` не устанавливает внешние движки; HTTP-сервисы нужно запустить отдельно.

| Движок | Назначение | Подключение |
| --- | --- | --- |
| LanguageTool | Орфография, грамматика, пунктуация, типографика | Локальный HTTP-сервер |
| Vale | Стиль и терминология по правилам | Внешняя программа; в пакете есть русские правила |
| LLM | Контекстные языковые гипотезы, стиль и остаточный английский | `llama-server` или Ollama; ChatGPT — отдельно и с согласием |

После настройки выбранных движков:

```powershell
uv run --locked language-review check ..\repo --engine languagetool --engine vale
uv run --locked language-review check ..\repo --engine llm --llm-provider ollama --category spelling --category grammar
uv run --locked language-review check ..\repo --engine vale --format json --output ..\check-report.json
```

`--engine` выбирает только перечисленные движки; без него действует профиль проекта (шаблон `init` включает LanguageTool, Vale и LLM). Провайдер LLM по умолчанию — `llama_cpp`; локальный вариант с Gemma 4 E4B описан в руководстве. Недоступный движок или выбранная модель не заменяются другими молча.

`check` сам выполняет извлечение и передаёт движкам только выбранные фрагменты. Технические токены и защищённые вставки маскируются, а координаты ответа отображаются обратно на исходник. Предложения со статусом `candidate` прошли программные проверки границ и содержимого, но требуют ручной проверки; `rejected` сохраняет причины отказа. Согласие движков не является общей вероятностью правильности.

### Сохранить ревью и проверить его актуальность

```powershell
uv run --locked language-review check ..\repo --engine vale --view review --format json --output ..\review.json
uv run --locked language-review show-review ..\review.json --all
uv run --locked language-review verify-review ..\review.json --root 'root-0001=..\repo' --format json
```

`--view review` выделяет приоритеты, отдельные свидетельства и риски, сохраняя полный результат `check`. Текстовое представление показывает первые десять замечаний; `--all` показывает все. `show-review` читает сохранённый JSON без повторного анализа. В `verify-review` укажите ID корня из отчёта и соответствующий каталог или файл: команда сверяет SHA-256, цитаты и координаты. Статус `current` подтверждает актуальность локализации, но не правильность диагноза или замены. Подробности — в [руководстве по ревью](docs/agent-review.md).

## Поддерживаемые форматы

| Файлы | Что извлекается | Существенные ограничения |
| --- | --- | --- |
| Rust (`.rs`), C# (`.cs`), C/C++ (`.c`, `.cpp`, `.cc`, `.cxx`, `.h`, `.hpp`, `.hh`, `.hxx`) | Комментарии, документационные комментарии, строки известных или настроенных вызовов сообщений | Неоднозначный `.h` даёт `partial`; `extract.header_language` позволяет выбрать `c` или `cpp` |
| PowerShell (`.ps1`, `.psm1`) | Комментарии, comment-based help, строки команд сообщений и here-strings | `.psd1` не разбирается как исполняемый код |
| Markdown (`.md`, `.markdown`) | Заголовки, абзацы, списки, GFM-таблицы и подписи ссылок | Цитаты и code blocks исключаются; неоднозначное сопоставление даёт `partial` |
| TXT, reStructuredText, AsciiDoc (`.txt`, `.rst`, `.adoc`) | Непустые строки TXT; заголовки и проза размеченных документов | Для reStructuredText и AsciiDoc поддерживается консервативное подмножество разметки |
| JSON, YAML, TOML, XML (`.json`, `.yaml`, `.yml`, `.toml`, `.xml`) | Только строковые значения по настроенным селекторам | Расширение нужно включить явно; без селектора фрагменты не извлекаются |

Все расширения из первых четырёх строк включены по умолчанию. Бинарные, слишком большие файлы и файлы с неподходящей кодировкой пропускаются с причиной. Повреждённый или неоднозначный синтаксис отмечается в отчёте; отсутствие надёжно извлечённого текста не выдаётся за полную проверку.

Для структурированных файлов добавьте расширение и селекторы в `.language-review.yaml`. Минимальный пример политики для Markdown и JSON:

```yaml
schema_version: 1
default_profile: everyday
scan:
  extensions: [.md, .json]
extract:
  selectors:
    .json: ['$.ui.message', '$.errors[*].description']
profiles:
  everyday:
    engines: [vale]
```

Селекторы поддерживают свойства `.name`, ключи `['name']` или `["name"]`, индексы обычного массива `[0]` и wildcard `*`; для XML доступны имена элементов и атрибуты `@name`. YAML tags/aliases не выполняются и не раскрываются, повторяющиеся JSON/YAML-ключи пропускаются с диагностикой. TOML-массивы таблиц (`[[table]]`) пока дают `partial`. Дополнительные вызовы сообщений задаются через `extract.message_calls`, например `[MyLogger.ShowMessage, logger->Notify]`.

## Конфигурация и диагностика

У настроек два владельца:

- **`.language-review.yaml` в корне цели** — профили, движки, категории, термины, модели, уровни рассуждения, режимы и бюджеты анализа, языковые промпты и `path_rules`. `--profile NAME` принудительно выбирает объявленный профиль; разовые CLI-параметры имеют высший приоритет.
- **Пользовательский TOML** (`%APPDATA%/language-review/config.toml`) и `--config TOML` — адреса сервисов, путь к Vale, OAuth, настройки памяти и отдельные согласия. Проектный YAML не выдаёт сетевых полномочий.

```powershell
uv run --locked language-review config show ..\repo --format json
uv run --locked language-review config show --environment --format json
uv run --locked language-review doctor --format json
uv run --locked language-review --config .\environment.toml check ..\repo --engine vale
```

Последний пример предполагает, что вы создали `environment.toml`. `config show` показывает эффективную проектную политику и источники значений, `config validate` проверяет её без движков. `doctor` диагностирует пользовательскую среду: пакет, Python, настроенные программы, HTTP-сервисы и движки. Ошибка диагностики внешнего движка сама по себе не мешает `scan`.

Поля, приоритеты, настройка промптов и миграция прежней политики TOML описаны в [проектной конфигурации](docs/project-configuration.md). В руководствах по движкам и расширенному анализу есть старые TOML-примеры политики: модели, термины и режимы из них нужно перенести в YAML-профиль; адреса и согласия остаются в TOML.

## Дополнительные возможности

- **[Многоступенчатый анализ](docs/multistage-analysis.md).** Режимы `normal`, `adaptive` и `deep`, стратегии поиска, отдельная критическая верификация гипотез, бюджеты и покрытие проходов. Добровольный Sign in with ChatGPT позволяет выбрать доступные аккаунту Luna/Sol и effort. OAuth-сессия сама по себе не разрешает передачу исходников.
- **[Предметная память](docs/memory.md).** Явно включаемая PostgreSQL/pgvector через Docker Compose, автоматический журнал `check`, решения `decide-review`, фоновая LLM-консолидация и гибридный recall. Работает с optional extra `memory`; базовый анализ не требует Docker или PostgreSQL. Уверенность модели не превращает гипотезу в подтверждённое решение.
- **[Независимая оценка](docs/evaluation.md).** Отдельная CLI `language-review-eval`: корпус, офлайн-оценка сохранённых check/review, раздельные detection/correction и coverage, сравнение baseline/candidate, слепая разметка и явный live capture. Руководство описывает стабильные `label_id` пакетов разметки 2.0, согласие разметчиков и версии метрик. Синтетический набор проверяет контракты оценщика; независимая оценка качества на реальном русском техническом корпусе пока не выполнена.

## Результаты, ограничения и безопасность

`scan`, `extract`, `check`, `show-review`, `verify-review`, `doctor` и `config show` не изменяют исследуемые исходники. `--output` явно сохраняет отчёт, `init` — проектную конфигурацию; включённая память отдельно записывает события в БД. **SARIF, анализ Git diff и применение исправлений не реализованы.**

По умолчанию текст передаётся только локальным сервисам. Для нелокальных endpoints нужно явное `check.allow_remote_endpoints = true`; облачный ChatGPT требует отдельного согласия на исходники и отдельного — на передачу памяти. Выбор провайдера в YAML и вход через OAuth не заменяют эти согласия. Реальные отчёты могут содержать исходный текст: не публикуйте их вместе с секретами и пользовательскими данными.

LanguageTool и Vale проверяют единицы с кириллицей. Полностью английскую прозу проверяет только LLM при включённой категории `untranslated_english`; технические идентификаторы не считаются такой прозой. Модель может пропускать ошибки и предлагать замены, меняющие смысл. Маскирование, проверки отрицаний и технического содержимого снижают риск, но не доказывают безопасность предложения.

### Отчёты и координаты

JSON `scan` содержит `schema_version`, сведения о программе и корнях, `files` и итоговые счётчики; состояния файлов — `selected`, `skipped`, `error`. Языковых находок в нём нет. `extract` сохраняет SHA-256, профиль, точные цитаты и защищённые диапазоны; состояния документа — `extracted`, `skipped`, `unsupported`, `partial`, `error`.

Схемы `scan` и `language-review.extract` имеют версию 1.0. `language-review.check` и `language-review.review` используют 1.0 для локального `normal` без верификации гипотез, 1.1 — для расширенных режимов, верификации или ChatGPT; читатели поддерживают обе версии. Схемы и примеры собраны [ниже](#документация-и-разработка).

Исходный `byte_offset` отсчитывается от 0 в оригинальных байтах, включая BOM; `line`, `column` и `utf16_column` — от 1. `column` считает Unicode code points (tab — одна колонка), `utf16_column` — UTF-16 code units; конец диапазона исключающий. Escape-последовательности сохраняются в исходном виде и защищаются отдельно. Эти координаты позволяют сверять замечания с байтами файла, а не искать похожую строку.

### Статусы и коды завершения

Для `check`: `clean` означает полную проверку без замечаний, `findings` — полную проверку с замечаниями, `partial` — неполное извлечение или проверку, `unavailable` — недоступный или сбойный движок, `error` — ошибку входных данных. При неполной проверке найденные замечания остаются в отчёте.

- `0` — успешное выполнение; для `check` — `clean`. Ожидаемые пропуски при инвентаризации не являются ошибкой.
- `1` — `check` выполнен полностью, есть замечания.
- `2` — неверные аргументы, входной путь, конфигурация или сохранённый review.
- `3` — ошибка ввода-вывода/записи отчёта; для `extract` также неполное или неподдерживаемое извлечение, для `doctor` — сбой настроенной внешней зависимости.
- `4` — неполный `check`/review; для `verify-review` — `stale` или `unverified`.
- `5` — выбранный движок `check` недоступен или завершился ошибкой.
- `6` — ошибка подсистемы памяти.
- `130` — операция прервана пользователем.

Код `0` у `show-review` означает успешное отображение сохранённого отчёта, а не отсутствие находок. Актуальность отчёта, полнота анализа и правильность языкового решения — разные проверки.
